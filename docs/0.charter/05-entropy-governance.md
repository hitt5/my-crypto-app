## 0. なぜ「気をつける」では止まらないか

エントロピー増大は怠慢の結果ではない。**善意の作業が構造的に生む副産物**である。

| 善意の行動 | 生む増大 |
| --- | --- |
| 分かりやすくするため文書を追加する | 同じ事実が 2 箇所になり、片方が腐る |
| 抜け漏れを防ぐため分類を足す | 「どちらの箱か」の裁定が発生し、全件が停止する |
| 状況を記録するためレポートを作る | 実体と乖離した MD が増え続ける |
| 整合させるため生成物を手で直す | 次の再生成で消え、実装と異なる嘘の地図が残る |

したがって統治は精神論ではなく**「増やせない構造」**として実装する。
本書はその 4 経路と封じ方を定める。

> **測り方の原則（WM-2 / P26）**: $H$ と $Meaning$ は**同時に**測る。
> 「整理した」「削減した」「統合した」を件数の減少だけで主張してはならない。
> **最も安価な $H$ 最小化は「意味を削ること」**であり、仕様や Evidence を消せば指標は改善する。
> これは Goodhart の法則そのものであり、改善ではなく破壊である。

## 1. 経路① 概念の増大 — 定義品質で統治する

### 数ではなく品質を規律する

かつては「概念数を凍結する」方式を採ったが、**これは失敗した**。宣言（凍結した集合）と実体
（実際に使われている概念）が乖離したまま固定され、**悪い定義を保存する**結果になったためである。

規律の対象は**概念の数ではなく、1 概念あたりの定義品質**である。

### ライフサイクル

```
draft ──→ proposed ──→ canonical ──→ deprecated
(起案可)   (品質バー   (Human 承認    (廃止。ID は
 型使用不可  機械 PASS)   のみ)         再利用しない)
```

Agent は `draft` の起案と `proposed` への機械昇格までを行える。
**`canonical` への昇格は Human 承認のみ**である。

### 昇格の品質バー（4 条件すべて必須）

| # | 条件 | 満たせないとき |
| --- | --- | --- |
| Q1 | **定義の明確性** — 定義が単独で「何であるか」を説明し、不変条件を 1 つ以上持つ | 定義が曖昧なので言語化し直す |
| Q2 | **弁別性** — 「既存のどれとも、この点で違う」を明記できる | 衝突しているなら統合候補 |
| Q3 | **上位アンカー** — World Model 十要素のいずれかに分類できる（WM-1 / P25） | 定義が曖昧か、世界モデル側の見直しが必要 |
| Q4 | **実在性** — 実インスタンスまたは具体的な適用予定がある | 使われない概念は作らない |

### 差分は写像で吸収する（新概念を作る前に試す順序）

| 順序 | 経路 | 使う場面 |
| --- | --- | --- |
| ① | **語彙の写像** | 呼び方が違うだけ（**第一選択**） |
| ② | **固有値として持つ** | 分類ではなく値の違い |
| ③ | Core へ `draft` 起案 | 普遍的に新しい概念（Q1-Q4 → HIL） |
| ④ | 領域パッケージとして分離 | その領域だけの概念（HIL・パッケージ単位） |

### 禁止（SC-1 〜 SC-7）

| # | 禁止 | 理由 |
| --- | --- | --- |
| SC-1 | 語彙差を概念差として直書きする | まず写像を試す。呼び方の違いを概念の違いにすると概念が増殖する |
| SC-2 | 領域固有値を共通概念へ列挙する | Core が特定領域の値に汚染され、他領域で使えなくなる |
| SC-3 | `draft` / `proposed` の概念を型として使用する | 未承認の定義が実データを縛ると、後から直せなくなる |
| SC-4 | 正準 ID の改名 | 参照が一斉に切れる。廃止は `deprecated` 遷移で行う |
| SC-5 | Human 承認なしに `canonical` へ昇格させる | Agent の自己承認は品質バーの意味を消す |
| SC-6 | シャドーオントロジーの作成 | 宣言・アンカー・承認を持たない自作体系は検証にかからない |
| SC-7 | 品質バー未達の概念を `canonical` 扱いする | 弁別性・アンカー未記載のまま正準化すると悪い定義が固定される |

検証 = `sdt.ontology_validate`。**ただし Q1-Q4 とライフサイクルの機械検査は未実装**であり、
現在は HIL レビューが代替する（P25 が ADVISORY である理由 / 実装済みと誤認しない）。

## 1.5 SDT の永続化規律（JF-1 〜 JF-4 / DL-R1 〜 DL-R4）

P10（二重 SoT 禁止）の施行細則。**禁止の本質は「DB 化」ではなく「正が 2 つになること」**である。

| # | 規律 | 内容 |
| --- | --- | --- |
| JF-1 | **記録系は JSON / MD が SoT** | 要求モデル・憲章・HIL 承認・trace の正本は SDT のファイルであり、DB へ authoritative に複製しない |
| JF-2 | **状態系は append-only ログが SoT** | task status / dd_progress / milestone / Issue status / Evidence は追記ログを正とし、JSON / DB の状態表現はいずれも再生成可能な投影に限る |
| JF-3 | **同一データ種別に正を 2 つ作らない** | 同じ種別へ JSON と DB の双方から authoritative 書込をしない |
| JF-4 | **層の移行は移行手順経由のみ** | replay + 旧側 read-only 化 + 収束検証を伴わない切替をしない |
| DL-R1 | **投影は再生成可能に保つ** | 投影物を手で直さない（P24）。直すのは上流であり、その後再生成する |
| DL-R2 | **欠測と実測 0 を区別する** | 観測できなかったことを 0 と記録しない（P27） |
| DL-R3 | **監査証跡は不可変** | 記録済みの Evidence を改変・削除しない |
| DL-R4 | **ノード間で状態を二重に持たない** | 複数実行面がある場合も、状態の書き手は 1 つに限る（= 04 §4 Single Writer） |

## 2. 経路② 生成物の手編集 — 書き込み主権で統治する

SDT には**人間が書くべきもの**と**機械が生成するので触ってはいけないもの**が混在する。
リリース計画は人間の意思決定であり手で書くのが正しい。一方 CallGraph はコードからの投影物で、
手で直せば次の再生成で消えるか、実装と乖離した嘘の地図になる。

### 2 軸で宣言する（1 軸では表現できない）

| 対象 | 手編集したら | 削除したら | 2 軸 |
| --- | --- | --- | --- |
| CallGraph / 導出グラフ | 次の再生成で消える（無効） | 再生成すれば戻る | `generator` × `derived` |
| Evidence / coverage / soak | 監査証跡の改竄 | **二度と戻らない** | `agent` × `captured` |

「触るな」の 1 軸に潰すと、**「消してよいか」が判定できなくなる**。

### 規範と事実を区別する

「誰が**書いてよいか**」は事前の規範、「誰が**書いたか**」は事後の事実である。
両者の食い違い（生成物なのに手編集の痕跡）は**手編集された物証**として検出できる。

### 解決の順序と Action

宣言は「ノード個別の上書き → レイアウト契約のパターン → 既定（未分類）」の順に解決する。
全ノードへ同じ宣言をコピーする二重管理を避けるため、**原則は契約で覆い、例外だけ個別宣言**する。

| Action | 用途 |
| --- | --- |
| `sdt.authoring_resolve` | **書く前に**主権を問う（可否 + 根拠） |
| `sdt.authoring_validate` | 全体検証（**完了ゲート**） |
| `sdt.authoring_classify` | 分類カバレッジと未分類一覧（HIL 入力） |
| `sdt.authoring_drift` | 生成物が手編集されていないかの照合 |

未分類への書き込みは**拒否（deny-by-default）**する。まず宣言を追加する（P24）。

## 3. 経路③ 文書の増殖 — 双対表現と参照最小主義

### MD と JSON は対で維持する（WM-5）

| 側 | 役割 |
| --- | --- |
| **MD** | 人間可読 view。規範文・意図・手順を持つ |
| **JSON** | 機械可読 SoT。構造・関係・status・検証対象を持つ |

**MD だけ / JSON だけを「正本」と呼ばない。** 両者が矛盾したときは、機械的な関係と status は
JSON、規範文と意図は MD を正とし、**片方を黙殺せず両方を同期補修する**。

### 参照リンク最小主義

| 規律 | 理由 |
| --- | --- |
| 本文末尾に「関連リンク」で物理パスを羅列しない | 移動・改名で一斉に切れる。切れても誰も気づかない |
| 参照関係は SDT が持つ（trace / spec_refs） | 本文に手書きすると二重管理になり、片方が腐る |
| 参照が必要なら論理 URI を使う | 物理配置の変更から独立できる |
| 参照先が移動したら解決器で修復する | 手で書き換えると registry と実体が乖離する |

### ゴミを作らないための問い

新しい文書・分類・レポートを作る前に、次を自問する。**1 つでも「いいえ」なら作らない。**

- [ ] この情報の**消費者**（人間 or 機械）が具体的に存在するか
- [ ] 既存の SoT に**同じ事実が既にない**か（あるならそこを直す）
- [ ] **腐ったときに検知される**場所に置かれるか（誰も見ない場所は必ず腐る）
- [ ] 生成物なら、**再生成の手順**が定義されているか

> **実測された教訓**: 施行規則層が監査対象に登録されておらず、コード・設定からの参照も 0 件
> だったため、**壊れても誰も気づかない場所**として黙って腐り、実在しないパス 30 件・
> 実在しない起動手順・実際には稼働していないポート宣言・1 文字違いの Action キーを抱えるに至った。
> **真因は内容の古さではなく、検知経路の不在だった。**

## 4. 経路④ ルール自体の増大 — 3 層と収録基準

ルールが増えると、**高優先のルールが低優先のルールに埋もれる**。注意は希少資源なので、
ルール群も階層化して「毎回読む量」を最小に保つ。

| 層 | 役割 | 読み込み |
| --- | --- | --- |
| 常時遵守層（L0） | 守るべき最小核だけを置く | 毎セッション |
| 索引層（L1） | トリガー → 該当する施行手順への索引（本文を持たない） | 状況が発生したとき |
| 施行層（L2） | 手順（MCP でも憲章でも代替できないものだけ） | 索引が指したときのみ |

### 収録の 3 分類（N/R/E）

| 分類 | 内容 | 書き方 |
| --- | --- | --- |
| **N**（規範） | 原則・禁止・判定基準 | その層が SoT。ここだけが本体 |
| **R**（事実） | ポート・パス・件数・在庫 | **値を書かない**。設定・カタログ・Action を参照する |
| **E**（執行） | その規範を検証する手段 | **実在する Action** を最低 1 つ。無ければ「宣言的原則」と明示 |

> **偽のゲートは、無いゲートより有害である**（CS-5）。実在しない Action を「HARD GATE」と
> 書くと、Agent は「ゲートは飾り」と学習し、その学習が**実在するゲートへ波及する**。

### ルールを変更するときの手順

1. **条項の追加・改訂・削除は 01 に対して行う**（他ファイルへ書かない）
2. 同一作業内で `rules.charter_sync` を実行し catalog を同期する（P21 / CS-3）
3. `rules.audit` で drift = 0 / missing_grounding = 0 を確認する
4. 名指した Action が実在することを確認する（Inventory で照合）
5. ファイルを追加・改名・削除したら索引を同時に更新する
