# 1.concept — コンセプト設計標準（Concept Blueprint）

> **これは各テーマの `1.concept/` が“どうあるべきか”を定義する標準（正本）です。**
> 新テーマを起こしたら、**このブループリントに沿って** 00〜05 の6ファイルを整備してください。
> **テーマ**: {{PROJECT_NAME}} / **theme_id**: `{{THEME_ID}}` / **profile**: `{{PROFILE}}` / **作成**: {{DATE}}

---

## なぜ標準が要るか

「各テーマのコンセプトがバラバラの構造で書かれる」と、テーマ間比較ができず、後続工程（データモデル→AGN→カタログ）も安定しません。**全テーマで同じ構造・同じ品質バー**に揃えるための型がこのブループリントです。

- 構成の生成はテンプレートが担う（フォルダとスケルトン）
- **中身の整備は本標準に従う**（何を・どの粒度で書くか）
- テーマの性質に迷ったら、まずルート `README.md` §1.1 の**プロジェクトタイプ**（A 戦略・仮説検証型 / B 業務改善型 / C リサーチ型 / D プロダクト開発型 / E モニタリング型）から最も近いものを選ぶ

## 整備の順序（推奨）

```text
① プロジェクトタイプを選ぶ（ルート README §1.1） → 00-overview
② 答えるべき問いを3つ前後に絞る                  → 00-overview
③ グラフ空間の設計を決める                       → 04-data-model §グラフ空間
   （単一空間で始めてよい。起点・時間軸・更新サイクル・
    確度が根本的に違う対象群が出てきたら空間を分ける）
④ ノード型・エッジ型＋不変条件を定義              → 04-data-model
⑤ 用語を 共通概念／固有語彙 に切り分ける           → 共通概念は据え置き / 固有は mappings/ へ
⑥ 課題・手段・進め方を肉付け                     → 01 / 02 / 03 / 05
⑦ HIL H1 承認に出す（この構造で進めてよいか）
```

## 設計ルール（Charter 由来・全テーマ共通）

| # | ルール | 根拠 |
|---|---|---|
| C1 | 中核対象は**検証可能な単位**（仮説・施策・主張・要求など）として管理し、「成立条件（いつ・何が満たされるべきか）」と「見直し条件（何を満たせなくなったら再検討するか）」を付す | 検証駆動 |
| C2 | 観測・評価・判断は**根拠となるソース参照を必須**にする（Evidence by default） | 根拠主義 |
| C3 | 起点・時間軸・更新サイクル・確度が根本的に異なる対象群は**別グラフ空間**に分ける（該当がなければ単一空間でよい） | 分離と結線 |
| C4 | Edge の別名を**独立レイヤーとして定義しない**（二重定義の禁止） | 分離と結線 |
| C5 | **固有語彙・固有値を共通概念パッケージに直書きしない**。写像（`mappings/<profile>.mapping.json`）へ吸収する | 語彙吸収 |
| C6 | 重要な意思決定は**人間のみ**が行う（HIL） | HILゲート |

## テーマ間比較を成立させる条件

同一の評価軸で複数テーマを回して比較するには、**評価軸・出力フォーマット・前提コンテキストの有無を揃え、変数を1つだけ変える**こと。コンセプトの構造がテーマ間で揃っていることが前提になる（＝本ブループリントの目的）。
